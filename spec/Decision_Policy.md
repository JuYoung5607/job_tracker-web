# Decision_Policy — 판정과 피드백 규칙 (v2)

## 판정의 세 축

1. 공고 사실 검증: 근거가 충분한가?
2. 공고 생애주기: active/changed/closed/unavailable/unknown 중 무엇인가?
3. 사용자별 적합도: 누구에게 어느 순서로 보일 것인가?

이 세 축은 서로의 상태값을 재사용하지 않는다. `recommended/rejected/review`를 JobPosting의 lifecycle_status로 저장하지 않는다.

## 검색과 후보

SearchConditions의 명시적 강한 조건만 검색 범위에 반영한다. PreferenceProfile의 학습된 가중치는 Planner의 목록 조회 범위를 자동으로 줄이지 않는다. 검색 예산은 상한이며 가능한 한 다양한 직무·출처를 탐색한다. URL 후보는 채용 공고 상세 페이지로 확인되기 전까지 공고가 아니다.

후보 큐의 전체 고유 URL 수는 목록 수집 결과와 목록 확장 결과를 합쳐 `SearchBudget.max_candidates` 이하로 제한한다. Iterator는 새 URL 병합 시 다시 중복·상한을 검사한다. 목록/종류 불명 페이지는 탐색 단서일 뿐 공고로 저장하지 않는다. 목록에서 상세 URL로의 확장은 한 단계만 허용하며, 상세 여부가 확인되지 않으면 Extractor·Job Persister로 진행하지 않는다. 후보별 실패는 오류로 기록하고 해당 후보를 완료 처리해 큐가 무한히 멈추지 않게 한다.

## 검증·공개

사용자 웹 피드에는 `eligible`과 `review`만 노출한다. `excluded`는 사용자에게 노출하지 않는다. `review`는 확정 추천이 아니라 근거가 부족한 검토 대상으로 표시하고, 어떤 조건이 불확실한지 이유를 함께 제공한다. `excluded`의 건수와 제외 사유는 개발·운영 진단 로그에만 남길 수 있으며 사용자 피드에는 전달하지 않는다. 별도 개인화 그래프의 Ranker와 Feed Publisher가 이 정책을 각각 확인한다.

핵심 필드(job_title, experience_level, closes_at, employment_type, location)는 원문 근거를 우선한다. 검증 결과는 verified, partial, conflict, missing으로 구분한다. 중요한 충돌/누락이 있으면 자동 공개를 보류하고 수동 검토 대상으로 보낸다. 수집 실패나 순간적인 접속 불가가 기존 정상 공고를 덮어쓰지 않는다. 회사 정보 보강 실패는 비차단이다.

신입·주니어 사용자의 `max_experience_years`가 설정돼 있으면, 원문에서 확인된 최소 요구 경력이 이를 초과하는 공고는 사용자 적합도에서 제외한다. 이미 지난 명시적 마감일이나 현재 공고의 명시적 마감 상태도 제외 사유다. 마감 여부 또는 경력의 근거가 없으면 적합하다고 추정하지 않고 `review`로 둔다. 날짜만 제시된 마감일은 한국 시간의 해당 날짜 종료까지 유효한 것으로 해석한다.

사용자가 `한국계 기업만`을 명시한 경우, 한국계 여부는 채용 사이트의 국적이나 한국 지사의 소재지가 아니라 **최종 모회사가 한국 기업인지**를 기준으로 판단한다. 현재 수집 그래프에는 이 검증이 아직 구현되지 않았다. 회사 계열 근거를 확인할 수 없으면 한국계로 추정하지 않고 검토 대상으로 남긴다.

## Lifecycle

새 공고는 active, 기존 내용이 달라지면 changed, 신뢰 가능한 폐쇄 근거가 있으면 closed, 접근 문제가 지속되면 unavailable, 판단할 근거가 부족하면 unknown이다. 단발성 오류만으로 closed를 확정하지 않는다. 상태 변경은 시각·근거·버전을 남긴다.

## Ranker (MVP)

- 명시적 제외·필수 조건은 우선 적용한다. 사용자가 직접 고른 값과 추론 선호가 충돌하면 직접 고른 값을 따른다.
- 후보 점수는 명시적 조건 적합도 + 직무 관련성 + 누적 선호 가중치로 계산해 0~1로 정규화한다. 이 수치는 취업 성공 확률이 아니다.
- 선호 가중치는 점수의 일부에만 제한한다. 피드백이 적을수록 영향력을 낮춘다.
- 낮은 점수는 삭제/폐기 사유가 아니다. 피드에 제한된 탐색 결과를 섞어 편향을 완화한다.
- 점수와 함께 사용된 특징·가중치·설명·프로필 버전을 저장해 재현 가능하게 한다.

정확한 계수와 탐색 비율은 설정값으로 두고 평가 데이터로 조정한다. 초기값을 정답처럼 명세에 고정하지 않는다.

## 피드백 처리

결정: interested(양성), not_interested(음성), hold(중립 또는 매우 약한 신호). 선택 이유는 여러 개일 수 있으며 category와 가능하면 value를 함께 기록한다. 예: `skill=Computer Vision`, `employment_type=계약직`. 이유 없는 클릭은 공고 전체에 대한 약한 신호로만 처리하고 임의의 기술·기업을 추론하지 않는다.

동일 피드백 요청은 멱등 처리한다. 사용자가 선택을 바꾸면 이전 피드백을 덮어버리지 않고 최신 선택/이력을 구분한다. Preference Updater는 이유가 명시된 특징에만 가중치를 주고 누적 횟수, 최근성, 상한, 신뢰도를 반영한다. 한 번의 부정 피드백으로 hard exclusion을 만들지 않는다. 명시적 검색 조건은 사용자가 직접 편집할 때만 바뀐다.

피드백 저장에 성공한 후에만 프로필을 갱신하고 해당 사용자의 피드를 재정렬한다. 다른 사용자의 점수에는 영향을 주지 않는다.

## 검토와 오류

자동 판정 근거가 부족하면 review 대기열로 보내고 공개 여부를 명확히 표시한다. 오류는 node, type, message, retryable, occurred_at으로 기록한다. 재시도는 예산과 지수 백오프를 따른다. LLM 출력은 항상 스키마 검증하며 추정·환각된 값으로 원문을 덮지 않는다.
